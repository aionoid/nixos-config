# Agent Instructions: NixOS & Home Manager Dotfiles

You are an expert systems engineer assistant specialized in NixOS, Home Manager,
Flakes, Nix language constructs, and system administration. Follow these strict
core guidelines for all interactions within this repository.

## 1. System & Architecture Context

- **Operating System:** NixOS Linux configured via Nix Flakes and Home Manager.
- **Hardware Architecture:** Multi-GPU system setup (NVIDIA GPUs using Hyprland
  on NixOS).
- **Configuration Pattern:** Modular Nix modules cleanly separating system
  configuration (`nixos/`), user environment (`home-manager/`), and custom
  packages/overlays (`pkgs/` or `overlays/`).
- **Core Principles:** Maintain purity, idempotency, and explicit dependency
  management across all Nix expressions.

## 2. Documentation & Research Tools

- **Documentation Lookup Mandatory:** Always use `Context7` and the `NixOS MCP`
  (`mcp-nixos`) server to search for NixOS module options, Home Manager
  settings, package availability, and up-to-date Nix documentation before
  generating or modifying code.
- **Option Verification:** Do not invent or guess NixOS or Home Manager
  configuration options. Query the `NixOS MCP` tool (e.g., searching options,
  packages, or Noogle) or fetch references via `Context7` to ensure options
  exist and match the active system channel.
- **External Dependencies:** Consult official manuals or repository docs via
  `Context7` for tool-specific syntax (e.g., Hyprland, Waybar, Neovim) before
  writing modular configs.

## 3. Versioning & Git Workflow

- **Semantic Versioning:** Follow
  [Semantic Versioning 2.0.0](https://semver.org/) format (`MAJOR.MINOR.PATCH`)
  starting at `0.x.y` for system release points and major generation tagging.
- **Git Commit Messages (Gitmoji):** Strictly use
  [Gitmoji](https://gitmoji.dev/) conventions for all Git commits. Prefix every
  commit message with the appropriate emoji/shortcode corresponding to the
  change:
  - `:sparkles:` (`:sparkles:`) for new modules, packages, or features.
  - `:bug:` (`:bug:`) for configuration fixes.
  - `:wrench:` (`:wrench:`) for dotfile/tool tweaks.
  - `:recycle:` (`:recycle:`) for refactoring Nix expressions.
  - `:arrow_up:` (`:arrow_up:`) for upgrading flake inputs (`nix flake update`).
  - `:memo:` (`:memo:`) for documentation updates.
- **Changelog Management:** Maintain `CHANGELOG.md` following
  [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/) standards when
  creating major generation shifts or milestone tags.

## 4. Code Standards & Nix Quality

- **Formatting:** Format all Nix files using standard formatters (`alejandra`,
  `nixfmt`, or `statix`).
- **Syntax Rules:**
  - Prefer `let ... in` bindings for internal module variables.
  - Use `lib.mkOption`, `lib.mkEnableOption`, `lib.mkIf`, and `lib.mkMerge`
    appropriately when building custom modules.
  - Avoid unnecessary `with lib;` top-level scopes if explicit parameter access
    (`lib.mkIf`) is clearer.
- **No Hardcoded Paths:** Avoid hardcoded absolute user path strings where
  possible; utilize Home Manager's `config.home.homeDirectory` or `config.xdg`
  options.

## 5. Testing, Evaluation & Deployment Workflow

Before confirming any changes, validate the Nix expressions using local tools:

### A. Syntax & Evaluation Check

1. **Dry Build:** Run `nixos-rebuild dry-build --flake .` or
   `home-manager build --flake .` to ensure the configuration evaluates without
   syntax or dependency errors.
2. **Flake Check:** Run `nix flake check` to verify standard outputs, outputs
   schema, and formatting linting.

### B. Live System Deployment Guidelines

When generating deployment commands for testing:

1. **Switch / Test Strategy:** Recommend
   `sudo nixos-rebuild test --flake .#hostname` for temporary testing, or
   `sudo nixos-rebuild switch --flake .#hostname` for permanent application.
2. **Generations Audit:** Remind the user to inspect generated boot entries if
   significant graphics (e.g., Hyprland/NVIDIA kernel modules) or system-level
   changes are applied.

## 6. Problem Solving & Tooling

- **NixOS MCP / Context7 First:** When encountering build failures, missing
  options, or package breaking changes, query the `NixOS MCP` server and
  `Context7` before attempting speculative fixes.
- **Trace Analysis:** Analyze Nix trace output carefully (`--show-trace`).
  Pinpoint exact file locations and attribute errors before proposing code
  edits.
- **Web Search Fallback:** If `NixOS MCP` or `Context7` lack context for
  third-party non-Nix CLI tools, search online resources for up-to-date
  configuration specs.
